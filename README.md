# КТК ЭЛОУ-АВТ — компьютерный тренажёрный комплекс

Тренажёр рабочего места оператора установки ЭЛОУ-АВТ с цифровым двойником
и ИИ-модулем. Решение кейса IT-чемпионата нефтяной отрасли 2026.

> Статус: **неделя 3**. Вход по логину и паролю с разграничением по ролям
> (Argon2id + JWT в cookie httpOnly), **экран разбора тренировки** (журнал,
> график телеметрии, ошибки, итоговая оценка), **администрирование**
> (учётные записи и просмотр журнала аудита), **замеренное время отклика**
> и автотесты. **ИИ-модуль** классифицирует и локализует ошибки оператора,
> объясняет их со ссылкой на техрегламент и предупреждает об аварии заранее
> по тренду параметров.
> Плюс с недели 2: сессии тренировки, сценарии с отказами по времени,
> полная схема БД (9 таблиц), оценка квалификации оператора.
> Матмодель — рабочая заглушка с чётким контрактом (зона Светланы).

## Запуск через Docker (рекомендуется — работает у всех одинаково)

Нужен только установленный **Docker Desktop**. Одна команда:

```bash
docker compose up --build
```

| Что | Адрес | Доступ |
|---|---|---|
| Тренажёр (рабочее место оператора) | http://localhost:8000 | operator / operator |
| pgAdmin (просмотр базы) | http://localhost:5050 | admin@ktk.local / admin |
| PostgreSQL | localhost:**5433** | база `ktk_eloyavt`, ktk / ktk |

Поднимаются три контейнера: `ktk-trainer`, `ktk-postgres`, `ktk-pgadmin`.
База стартует первой, приложение ждёт её готовности (healthcheck), само создаёт
таблицы и наполняет начальными данными (пользователи, сценарии, эталонные шаги).
Данные сохраняются в volume `ktk_pgdata`. Остановить: `Ctrl+C`;
удалить начисто вместе с базой: `docker compose down -v`.

Внешний порт БД — 5433, чтобы не конфликтовать с локально установленным
PostgreSQL на 5432.

### Если PostgreSQL уже установлен локально (без Docker)

```bash
bash scripts/create_local_db.sh     # создаст роль ktk и базу ktk_eloyavt
export DATABASE_URL=postgresql+asyncpg://ktk:ktk@localhost:5432/ktk_eloyavt
uvicorn backend.main:app --reload
```

## Запуск без Docker (локально, SQLite)

```bash
./run.sh            # venv + зависимости + сервер, БД = SQLite
# открыть http://localhost:8000
```

Вручную:
```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn backend.main:app --reload
```

БД выбирается переменной `DATABASE_URL` (по умолчанию SQLite):
`postgresql+asyncpg://ktk:ktk@localhost:5432/ktk` — Postgres,
`sqlite+aiosqlite:///./ktk.db` — локальный файл.

## Доступ и роли

Вход обязателен: без него закрыты и REST, и канал тренировки. Учебные
учётные записи создаются автоматически, пароль совпадает с логином.

| Логин | Роль | Что доступно |
|---|---|---|
| `operator` | оператор | своя тренировка, свой журнал и своя оценка |
| `instructor` | инструктор | + все тренировки, эталонные шаги, разбор |
| `admin` | администратор | + учётные записи и журнал аудита (`/admin`) |

Эталонные шаги (`/api/scenarios/{code}/reference`) закрыты от оператора
намеренно: это «ответы» к сценарию, их показывают только на разборе.

> **Где проходит граница.** До и во время тренировки эталон обучаемому
> недоступен. После завершения он видит балл и сводку («выполнено 1 из 2»),
> а правильную последовательность — только после того, как инструктор нажмёт
> «Открыть разбор обучаемому» (`POST /api/sessions/{id}/release`).
>
> Без этого оставалась лазейка: начать тренировку, сразу её завершить и
> прочитать «ответы» в собственной оценке. Шаги закрыты во всех трёх местах,
> где оценка попадает к обучаемому: в разборе, в `/assessment` и в сообщении,
> которое приходит по WebSocket сразу после «Завершить».
>
> Полный эталон сценария (все шаги с нормативами, в том числе для ещё не
> пройденных сценариев) остаётся только у инструктора и администратора.

Как это сделано (критерий ИБ):

- пароли — **Argon2id** (`argon2-cffi`), не SHA-256 и не открытый текст;
  старые SHA-256-хеши распознаются и переводятся в Argon2id при первом
  входе, сбрасывать пароли на существующих базах не нужно;
- сеанс — **JWT (HS256) в cookie httpOnly + SameSite=Strict**. Cookie
  выбрана осознанно: браузерный WebSocket не умеет передавать заголовок
  `Authorization`, а cookie уходит и в REST, и в WS-рукопожатии;
- **защита от подбора**: 5 неудачных попыток за 15 минут → блокировка
  учётной записи на 5 минут (ответ `429` с заголовком `Retry-After`);
- **аудит** в таблице `audit_log`: `login_success`, `login_failed`,
  `login_blocked`, `logout`, `access_denied`, `password_rehashed`,
  `session_start`, `session_end`, `user_created`, `user_updated`,
  `password_reset`, `debrief_released` — с пользователем, IP и User-Agent.
  Журнал читается администратором в `/admin`, а не только пишется;
- ответы на неверный пароль и на несуществующий логин совпадают —
  перебором нельзя выяснить существующие учётные записи.

Настройка через переменные окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `KTK_SECRET_KEY` | отладочный ключ | ключ подписи токенов. **В эксплуатации задать обязательно** |
| `KTK_COOKIE_SECURE` | `0` | `1` — отдавать cookie только по HTTPS |
| `KTK_SESSION_TTL_HOURS` | `8` | срок жизни сеанса (рабочая смена) |
| `KTK_MAX_FAILED_ATTEMPTS` | `5` | порог блокировки |
| `KTK_LOCKOUT_S` | `300` | длительность блокировки, с |
| `KTK_PASSWORD_OPERATOR` и др. | = логин | пароли учебных учётных записей |
| `KTK_MIN_PASSWORD_LENGTH` | `8` | минимальная длина пароля, назначаемого администратором |
| `KTK_TICK_PERIOD_S` | `1.0` | такт выдачи телеметрии, с. Один такт = 1 с модельного времени, поэтому значение меньше единицы ускоряет тренировку (используется в автотестах и замерах) |

## Лицензии и импортонезависимость

Кейс требует отечественных или патентно чистых технологий, а ОС и СУБД — из
реестра российского ПО. Полный разбор с лицензиями каждой зависимости —
в [`docs/stack.md`](docs/stack.md). Коротко:

- все зависимости под **MIT / BSD / Apache-2.0**, копилефта (GPL, AGPL, LGPL)
  нет ни одной;
- **интерфейс без внешних библиотек** — 1018 строк своего HTML, SVG и
  JavaScript, ни одного обращения к CDN. Рабочее место оператора стоит в
  закрытом сегменте без интернета, где страница с внешней библиотекой просто
  не отрисуется;
- приложение **не обращается ни к одному внешнему сервису** во время работы;
- где не соответствуем: стенд поднят на Ubuntu, а не на Astra Linux, и
  используется PostgreSQL из upstream, а не Postgres Pro. Оба пункта — про
  среду, а не про код: специфичных для upstream расширений в схеме нет, и то,
  что код не завязан на одну реализацию СУБД, проверяется на каждый push
  прогоном тестов на двух базах.

## Развёртывание на сервере

Стенд поднимается на небольшой машине: 1 ядро, 1 ГБ ОЗУ, Ubuntu 22.04/24.04
с Docker и nginx. Два шага:

```bash
git clone -b claude/roles-auth-training-review-i9u90o \
    https://github.com/mranton152/itchamp.git /opt/ktk
sudo bash /opt/ktk/deploy/install.sh itchamp.root72.ru

# когда домен уже указывает на сервер:
sudo bash /opt/ktk/deploy/enable-https.sh itchamp.root72.ru
```

`install.sh` идемпотентен — он же выкладывает обновления: забирает свежий код,
пересобирает образ и перезапускает стек, не трогая базу и пароли.

Расход памяти: PostgreSQL ~120 МБ, приложение ~110 МБ, nginx ~15 МБ.

### Чем боевой стек отличается от `docker-compose.yml`

Корневой файл предназначен для разработки, на общедоступном сервере он не
годится. `deploy/docker-compose.prod.yml`:

- **без pgAdmin** — на разработке он удобен, здесь это самый прожорливый
  контейнер стека (300–400 МБ) при 1 ГБ на всё;
- **порты не торчат наружу** — приложение слушает `127.0.0.1`, публикует его
  nginx; порт PostgreSQL не публикуется вовсе;
- **пароли и ключ подписи генерируются** при установке и лежат в
  `deploy/.env` (в git и в образ не попадает). Пароли учебных записей по
  умолчанию совпадают с логинами — на общедоступном стенде это открытая дверь,
  поэтому `install.sh` задаёт случайные до первого запуска и печатает их один
  раз. Менять их потом нужно в разделе `/admin`: `seed` наполняет таблицу
  только на пустой базе;
- **заданы пределы памяти** — при утечке умрёт контейнер, а не весь сервер;
- **PostgreSQL настроен под малую память** параметрами запуска.

Порт приложения переопределяется, если 8000 на сервере занят:
`APP_PORT=8010 sudo -E bash deploy/install.sh <домен>`.

### Автоматическая выкладка

После `install.sh` можно связать репозиторий со стендом: каждый push в ветку
стенда сам обновляет сайт. Один раз на сервере:

```bash
sudo bash /opt/ktk/deploy/setup-ci-deploy.sh itchamp.root72.ru
```

Скрипт напечатает три значения — их нужно добавить в GitHub: **Settings →
Secrets and variables → Actions**: `DEPLOY_HOST`, `DEPLOY_PORT`,
`DEPLOY_SSH_KEY`.

Дальше `.github/workflows/tests.yml` выкладывает стенд **последним заданием,
после зелёных тестов и успешной сборки образа**. Порядок именно такой не для
красоты: стендом пользуется вся команда, и сломанный коммит на нём хуже, чем
выкладка на пару минут позже.

Как это устроено и почему так:

- **выкладывает не root.** Отдельный пользователь `ktkdeploy`, которому `sudo`
  разрешает ровно одну команду без аргументов. Ключ лежит в секретах GitHub, и
  его утечка не должна означать полный доступ к серверу;
- **скрипт обновления живёт в `/usr/local/sbin/ktk-update`, а не в
  репозитории.** Выкладка делает `git reset --hard` и переписывает файлы;
  bash читает скрипт по мере выполнения, и подмена на середине сломала бы
  запуск;
- **при неудаче — откат.** Если после пересборки стенд не отвечает, `ktk-update`
  возвращает прежний коммит и поднимает его обратно;
- **отпечаток сервера закрепляется** (`ssh-keyscan`), а не отключается
  проверка ключа хоста;
- **выкладки не накладываются** (`concurrency`): на сервере одно ядро.

Отозвать доступ, если ключ утёк:
`sudo rm /home/ktkdeploy/.ssh/authorized_keys`.

Выложить руками, без GitHub: `sudo /usr/local/sbin/ktk-update`.

### nginx и WebSocket

Канал тренировки `/ws` требует проксирования апгрейда — иначе рабочее место
подключится и тут же отвалится. Конфигурация в `deploy/nginx-ktk.conf`
проставляет `Upgrade`/`Connection` и поднимает `proxy_read_timeout` до часа:
телеметрия идёт только на запущенном сценарии, и при стандартных 60 секундах
nginx рвал бы соединение оператору, который открыл рабочее место и не спешит.
`X-Forwarded-For` передаётся — приложение пишет IP в журнал аудита именно
оттуда.

`KTK_COOKIE_SECURE=1` включается только вторым шагом, после выпуска
сертификата: до появления HTTPS браузер перестал бы отдавать cookie сеанса,
и вход сломался бы.

## ИИ-модуль

`backend/ai_module.py` — классификация и локализация ошибок оператора,
интерпретируемое объяснение и прогноз риска.

**Справочник классов** (`CATALOGUE`). Каждый класс несёт не только код, но и
последствие со ссылкой на пункт техрегламента установки. Обучаемому нечего
понять из строки `low_level_drain`; ему нужно знать, что падение уровня
приводит к срыву печных насосов и прогару змеевика (разд. 7.7.1.14 и 7.10.3).

**Действия, а не только показания.** Модуль видит команды оператора и
разбирает их в контексте: открыть клапан при выводе на режим — штатная
операция, открыть его же при растущем давлении — грубая ошибка. По одним
показаниям приборов эти два случая неразличимы.

**Прогноз риска.** По скользящему окну методом наименьших квадратов
считается скорость изменения параметра и время до аварийной уставки.
Предупреждение приходит **до** срабатывания сигнализации, а `risk_score`
растёт по мере приближения. Одной разности соседних снимков здесь мало: в
показаниях есть пульсация, и знак тренда скакал бы каждый такт.

Как это выглядит на одной тренировке (сценарий «Рост давления»):

| t, с | Что говорит ИИ |
|---:|---|
| 1 | параметры в норме |
| 11 | *прогноз:* давление выйдет за уставку, до неё ≈ 27 с |
| 13 | **ошибка** `load_increase_under_alarm` — оператор увеличил подачу под предупреждением |
| 19 | **авария** `pressure_runaway` со ссылкой на разд. 7.7.1.16 |

### Почему база знаний, а не обученная модель

Размеченных тренировок пока нет. Классификатор, обученный на синтетике,
выдавал бы уверенные ответы, ни на чём не основанные, — а критерий требует
объяснимости. Правила опираются на техрегламент, проверяемы и защитимы.

При этом данные для обучения копятся с каждой тренировкой: `operator_actions`,
`telemetry` и `detected_errors` — это готовая разметка, где справочник классов
задаёт целевую переменную. Когда наберётся статистика, `_classify_state`
заменяется обученной моделью (scikit-learn, локально) без изменения контракта;
место замены отмечено в коде.

## Разбор тренировки

`/debrief` — экран, на котором инструктор и обучаемый разбирают проведённую
тренировку. Открывается из рабочего места кнопкой «Разбор», а сразу после
завершения — ссылкой в карточке результата.

Что показывает:

- **шапка** — сценарий, обучаемый, модельное и реальное время, состояние;
- **график телеметрии** — давление, температура, расход и уровень; каждый
  параметр масштабируется по своему диапазону, иначе уровень в процентах
  не разглядеть рядом с температурой в сотнях градусов. Красные полосы —
  интервалы с активной аварией, штрихи снизу — действия оператора,
  при наведении — значения на выбранной секунде;
- **итоговую оценку** — балл, вердикт, из чего сложился штраф, и разбор по
  эталонным шагам: что выполнено, что с опозданием, что пропущено;
- **найденные ошибки** — выход ИИ-модуля, сведённый в эпизоды: длящаяся
  авария показывается одной строкой «t=40…45 c · 6 замеров», а не шестью
  одинаковыми записями;
- **журнал действий** — что и когда нажимал обучаемый, с временем реакции;
- **эталонную последовательность** — только инструктору и администратору.

Обучаемому разбор эталонных шагов открывает инструктор кнопкой «Открыть разбор
обучаемому» — до этого видны балл и сводка (см. «Где проходит граница» выше).

Оценка формируется при завершении тренировки — в том числе при обрыве связи,
чтобы прерванная тренировка не оставалась без разбора.

### Методика оценки

100 баллов минус штрафы; порог сдачи — 70.

| Нарушение | Штраф |
|---|---:|
| Пропущен критический эталонный шаг | −20 |
| Пропущен обычный шаг | −8 |
| Шаг выполнен позже норматива | −5 |
| Критическая ошибка (severity=error) | −25 |
| Прочая ошибка ИИ | −8 |

Шаги сверяются по порядку: на установке важен не только набор операций, но и
их очерёдность (техрегламент, разд. 7.7.1.1). Ошибки считаются эпизодами, а не
записями, — иначе балл зависел бы от длительности аварии, а не от числа
промахов оператора. Веса заданы в `backend/storage.py` (`PENALTY`) и
уточняются вместе с Константином по мере развития ИИ-модуля.

## Администрирование

`/admin` — раздел администратора: учётные записи и журнал аудита. Кнопка
«Администрирование» в шапке видна только роли `admin`.

**Учётные записи.** Завести, сменить ФИО и роль, отключить, назначить пароль.
Пароли и их хеши наружу не отдаются вообще — ни в списке, ни в аудите. Логин
ограничен латиницей, цифрами и `_ . -`: он попадает в журнал и в имена учётных
записей на стенде. Минимальная длина назначаемого пароля — 8 символов
(`KTK_MIN_PASSWORD_LENGTH`); учебные записи из `seed.py` короче намеренно и на
стенде подлежат смене.

Отключение и смена роли действуют **немедленно**: пользователь восстанавливается
из БД на каждом запросе, а не берётся из токена, поэтому выданный ранее токен
сразу теряет прежние права. Перевходить не нужно, а отключённый пользователь
теряет доступ, не дожидаясь истечения сеанса.

Администратор не может изменить собственную роль или отключить сам себя —
иначе он запер бы себя снаружи. Отдельной проверки «остался последний
администратор» нет намеренно: она недостижима. Снять права может только
действующий администратор, а себя он тронуть не вправе, значит после любого
изменения сам вызывающий остаётся администратором — хотя бы один есть всегда.

**Журнал аудита.** Раньше `audit_log` только писался, и требование «вести
аудит» выполнялось формально: посмотреть записи было нечем. Теперь журнал
читается с фильтрами по пользователю и событию, свежие записи первыми, с
расшифровкой событий и подстановкой логина по `user_id`.

Кто что сделал, фиксируется в том числе для самих административных действий:
`user_created`, `user_updated`, `password_reset`, `debrief_released` — с
автором изменения, а не с тем, кого меняли.

## Время отклика и задержки

Замеряется скриптом, цифры — в [`docs/performance.md`](docs/performance.md):

```bash
python scripts/measure_latency.py --out docs/performance.md      # поднимет сервер сам
python scripts/measure_latency.py --url http://localhost:8000    # по готовому стенду
```

Ключевое (p95, SQLite, клиент и сервер на одной машине):

| Показатель | Норматив | Факт |
|---|---:|---:|
| Отклик на команду оператора | ≤ 200 мс | ~7 мс |
| Открытие разбора получасовой тренировки | ≤ 300 мс | ~93 мс |
| Период выдачи телеметрии | 1000 ± 50 мс | ~1001 мс |
| Вход в систему (Argon2id) | ≤ 500 мс | ~70 мс |

Такт телеметрии отсчитывается от расписания, а не от конца обработки, поэтому
задержка не накапливается: за длинную тренировку модельное время не расходится
с реальным.

## Автотесты

```bash
pip install -r requirements.txt -r requirements-dev.txt
pytest                                   # на SQLite, сервер БД не нужен

# тот же набор на настоящей базе
DATABASE_URL=postgresql+asyncpg://ktk:ktk@127.0.0.1:5432/ktk_test pytest
```

Два прогона — не для симметрии. SQLite почти не проверяет типы: время со
смещением в колонке без пояса он принимал молча, а PostgreSQL отказался
наполнять таблицу пользователей, и стенд не поднялся. Ошибка вскрылась при
развёртывании, а не в разработке. Теперь оба прогона идут в CI
(`.github/workflows/tests.yml`), третьим заданием там собирается и проверяется
боевой образ — сборку на сервере с одним ядром лучше не отлаживать.

117 тестов: вход и отказ во входе, блокировка подбора, проверка подписи токена,
разграничение по ролям, закрытость WebSocket, записи в аудите, состав разбора,
методика оценки (порядок шагов, пропуск критического, эпизоды ошибок),
открытие разбора инструктором, администрирование учётных записей и журнал
аудита, устойчивость — закрытие тренировки при обрыве связи и при сбросе, а также
ИИ-модуль: классификация, объяснения со ссылкой на регламент, разбор действий
в контексте и прогноз риска.

## Как модули стыкуются

- Движок (`engine.step()`) → отдаёт `ParameterState` → уходит в UI и в ИИ.
- ИИ (`ErrorAnalyzer.analyze()`) → отдаёт `AIFeedback` → уходит в UI.
- UI → шлёт `ControlCommand` → в движок; действия пишутся в журнал (`OperatorAction`).
- Сессия (`TrainingSession`) → загружает сценарий, применяет отказы по времени,
  пишет журнал и телеметрию в БД через `storage.py`.

Все схемы — в `backend/models.py`. Пока внешний контракт не меняется,
каждый дорабатывает свой модуль независимо.

## REST и WebSocket API

Все запросы, кроме входа и страницы входа, требуют действующего сеанса.

| Метод | Кому | Назначение |
|---|---|---|
| `POST /api/login` | всем | вход, ставит cookie сеанса |
| `POST /api/logout` | всем | выход, удаляет cookie |
| `GET /api/me` | вошедшим | текущий пользователь и роль |
| `GET /login` | всем | страница входа |
| `GET /` | вошедшим | интерфейс оператора (иначе → `/login`) |
| `GET /debrief` | вошедшим | экран разбора тренировки |
| `GET /api/scenarios` | вошедшим | список учебных сценариев |
| `GET /api/scenarios/{code}/reference` | инструктор, admin | эталонные шаги (для ИИ и разбора) |
| `GET /api/sessions` | вошедшим | тренировки: оператору свои, инструктору все |
| `GET /api/sessions/{id}/journal` | владельцу, инструктору | журнал действий |
| `GET /api/sessions/{id}/errors` | владельцу, инструктору | ошибки, выявленные ИИ |
| `GET /api/sessions/{id}/assessment` | владельцу, инструктору | оценка квалификации |
| `GET /api/sessions/{id}/telemetry` | владельцу, инструктору | история параметров (график) |
| `GET /api/sessions/{id}/debrief` | владельцу, инструктору | разбор целиком, одним ответом |
| `POST /api/sessions/{id}/release` | инструктор, admin | открыть разбор эталонных шагов обучаемому |
| `GET /admin` | вошедшим | экран администрирования (данные закрыты ролью) |
| `GET /api/users` | admin | учётные записи |
| `POST /api/users` | admin | завести учётную запись |
| `PATCH /api/users/{id}` | admin | ФИО, роль, отключение |
| `POST /api/users/{id}/password` | admin | назначить пароль |
| `GET /api/audit` | admin | журнал аудита с фильтрами |
| `GET /api/audit/events` | admin | виды событий для фильтра |

`WS /ws` — канал тренировки в реальном времени, требует сеанса (cookie уходит
вместе с рукопожатием; без неё канал закрывается кодом **4401**).
От UI: `{"session_action":"start","scenario":"pump_trip"}`,
`{"session_action":"reset"}`, `{"session_action":"stop"}` и команды оператора
`{"action":"set_valve","value":40}`. От сервера: `state` / `feedback` / `action`.
