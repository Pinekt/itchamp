# КТК ЭЛОУ-АВТ — компьютерный тренажёрный комплекс

Тренажёр рабочего места оператора установки ЭЛОУ-АВТ с цифровым двойником
и ИИ-модулем. Решение кейса IT-чемпионата нефтяной отрасли 2026.

> Статус: **неделя 3**. Вход по логину и паролю с разграничением по ролям
> (Argon2id + JWT в cookie httpOnly), аудит действий, автотесты.
> Плюс с недели 2: сессии тренировки, сценарии с отказами по времени,
> полная схема БД (9 таблиц), оценка квалификации оператора.
> ИИ и матмодель — рабочие заглушки с чётким контрактом.

## Запуск через Docker (рекомендуется — работает у всех одинаково)

Нужен только установленный **Docker Desktop**. Одна команда:

```bash
docker compose up --build
```

| Что | Адрес | Доступ |
|---|---|---|
| Тренажёр (рабочее место оператора) | http://localhost:8000 | operator / operator |
| pgAdmin (просмотр базы) | http://localhost:5050 | admin@ktk.local / admin |
| PostgreSQL | localhost:**5433** | база `ktk_eloyavt`, ktk / ktk |

Поднимаются три контейнера: `ktk-trainer`, `ktk-postgres`, `ktk-pgadmin`.
База стартует первой, приложение ждёт её готовности (healthcheck), само создаёт
таблицы и наполняет начальными данными (пользователи, сценарии, эталонные шаги).
Данные сохраняются в volume `ktk_pgdata`. Остановить: `Ctrl+C`;
удалить начисто вместе с базой: `docker compose down -v`.

Внешний порт БД — 5433, чтобы не конфликтовать с локально установленным
PostgreSQL на 5432.

### Если PostgreSQL уже установлен локально (без Docker)

```bash
bash scripts/create_local_db.sh     # создаст роль ktk и базу ktk_eloyavt
export DATABASE_URL=postgresql+asyncpg://ktk:ktk@localhost:5432/ktk_eloyavt
uvicorn backend.main:app --reload
```

## Запуск без Docker (локально, SQLite)

```bash
./run.sh            # venv + зависимости + сервер, БД = SQLite
# открыть http://localhost:8000
```

Вручную:
```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
uvicorn backend.main:app --reload
```

БД выбирается переменной `DATABASE_URL` (по умолчанию SQLite):
`postgresql+asyncpg://ktk:ktk@localhost:5432/ktk` — Postgres,
`sqlite+aiosqlite:///./ktk.db` — локальный файл.

## Доступ и роли

Вход обязателен: без него закрыты и REST, и канал тренировки. Учебные
учётные записи создаются автоматически, пароль совпадает с логином.

| Логин | Роль | Что доступно |
|---|---|---|
| `operator` | оператор | своя тренировка, свой журнал и своя оценка |
| `instructor` | инструктор | + все тренировки, эталонные шаги, разбор |
| `admin` | администратор | + пользователи и сценарии |

Эталонные шаги (`/api/scenarios/{code}/reference`) закрыты от оператора
намеренно: это «ответы» к сценарию, их показывают только на разборе.

Как это сделано (критерий ИБ):

- пароли — **Argon2id** (`argon2-cffi`), не SHA-256 и не открытый текст;
  старые SHA-256-хеши распознаются и переводятся в Argon2id при первом
  входе, сбрасывать пароли на существующих базах не нужно;
- сеанс — **JWT (HS256) в cookie httpOnly + SameSite=Strict**. Cookie
  выбрана осознанно: браузерный WebSocket не умеет передавать заголовок
  `Authorization`, а cookie уходит и в REST, и в WS-рукопожатии;
- **защита от подбора**: 5 неудачных попыток за 15 минут → блокировка
  учётной записи на 5 минут (ответ `429` с заголовком `Retry-After`);
- **аудит** в таблице `audit_log`: `login_success`, `login_failed`,
  `login_blocked`, `logout`, `access_denied`, `password_rehashed`,
  `session_start`, `session_end` — с пользователем, IP и User-Agent;
- ответы на неверный пароль и на несуществующий логин совпадают —
  перебором нельзя выяснить существующие учётные записи.

Настройка через переменные окружения:

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `KTK_SECRET_KEY` | отладочный ключ | ключ подписи токенов. **В эксплуатации задать обязательно** |
| `KTK_COOKIE_SECURE` | `0` | `1` — отдавать cookie только по HTTPS |
| `KTK_SESSION_TTL_HOURS` | `8` | срок жизни сеанса (рабочая смена) |
| `KTK_MAX_FAILED_ATTEMPTS` | `5` | порог блокировки |
| `KTK_LOCKOUT_S` | `300` | длительность блокировки, с |
| `KTK_PASSWORD_OPERATOR` и др. | = логин | пароли учебных учётных записей |

## Как модули стыкуются

- Движок (`engine.step()`) → отдаёт `ParameterState` → уходит в UI и в ИИ.
- ИИ (`ErrorAnalyzer.analyze()`) → отдаёт `AIFeedback` → уходит в UI.
- UI → шлёт `ControlCommand` → в движок; действия пишутся в журнал (`OperatorAction`).
- Сессия (`TrainingSession`) → загружает сценарий, применяет отказы по времени,
  пишет журнал и телеметрию в БД через `storage.py`.

Все схемы — в `backend/models.py`. Пока внешний контракт не меняется,
каждый дорабатывает свой модуль независимо.

## REST и WebSocket API

Все запросы, кроме входа и страницы входа, требуют действующего сеанса.

| Метод | Кому | Назначение |
|---|---|---|
| `POST /api/login` | всем | вход, ставит cookie сеанса |
| `POST /api/logout` | всем | выход, удаляет cookie |
| `GET /api/me` | вошедшим | текущий пользователь и роль |
| `GET /login` | всем | страница входа |
| `GET /` | вошедшим | интерфейс оператора (иначе → `/login`) |
| `GET /api/scenarios` | вошедшим | список учебных сценариев |
| `GET /api/scenarios/{code}/reference` | инструктор, admin | эталонные шаги (для ИИ и разбора) |
| `GET /api/sessions` | вошедшим | тренировки: оператору свои, инструктору все |
| `GET /api/sessions/{id}/journal` | владельцу, инструктору | журнал действий |
| `GET /api/sessions/{id}/errors` | владельцу, инструктору | ошибки, выявленные ИИ |
| `GET /api/sessions/{id}/assessment` | владельцу, инструктору | оценка квалификации |

`WS /ws` — канал тренировки в реальном времени, требует сеанса (cookie уходит
вместе с рукопожатием; без неё канал закрывается кодом **4401**).
От UI: `{"session_action":"start","scenario":"pump_trip"}`,
`{"session_action":"reset"}`, `{"session_action":"stop"}` и команды оператора
`{"action":"set_valve","value":40}`. От сервера: `state` / `feedback` / `action`.
